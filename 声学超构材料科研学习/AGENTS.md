# 声学学习项目约定

当用户说“继续声学学习”“查看学习项目”或讨论本目录中的声学资料时，先阅读：

1. `README.md`
2. `02_项目管理/项目状态.md`
3. `02_项目管理/交接日志/` 中日期最新的日志（如存在）

## 项目结构与文件归属

- 全部学习笔记放在 `01_学习笔记/`，只分三类：
  - `声学基础/`
  - `数学物理方法/`
  - `综述阅读/`
- 不创建、不维护独立术语表。概念及其必要英文原名直接写入相应笔记的解释主线。
- `02_项目管理/项目状态.md` 与 `02_项目管理/交接日志/` 共同管理续接信息。
- 所有图示、位图和 PDF 页面图统一放在 `03_图示/`：
  - 可嵌入 SVG 放在 `03_图示/SVG/`
  - 位图导出或截图放在 `03_图示/位图/`
  - PDF 页面或页面裁图放在 `03_图示/PDF页面图/`
- 不创建 `tmp/`、`素材/` 或其他平行图片目录。已使用的图片必须纳入 `03_图示/` 管理。
- `声学科研学习资源/` 是用户放入的原始 PDF、书籍、论文和配套注解，视为只读资料；不要改名、改写或移动其中的原始材料。

## 学习与笔记原则

- 用户自己决定每天学到哪里；不要创建按天、按周或按时长的学习计划。
- 以理解声学超构材料、线性与非线性声学为目标选择声学基础和数学物理方法内容；习题只用于验证理解，不把笔记写成应试提纲。
- 对话中的解释优先于笔记。必须先把问题讲清楚，再将已确认的理解、待解问题、必要概念和资料定位写入项目笔记。
- 笔记允许重写、重组和删除旧表述，不维护只增不减的流水账。
- 只有用户明确说“写交接日志”、准备开新对话或指出上下文不足时，才创建交接日志并更新项目状态；不要为每次对话自动写日志。
- 新交接日志使用 `YYYY-MM-DD-交接.md` 文件名，并同步更新 `../项目状态.md` 的当前续接点。

## Markdown 与数学格式

- 输出 Markdown 笔记时面向 Obsidian：行内公式使用 `$...$`，独立公式使用 `$$...$$`。
- Codex 聊天回复中：行内公式使用 `\(...\)`，独立公式使用 `$$...$$`。
- 不用 Unicode 数学记号代替公式。
- 需要空间关系、波形或结构图时，在 `03_图示/SVG/` 创建或更新可嵌入 SVG；只有交互确有价值时才创建 HTML。禁止 ASCII 绘图。

## 教学型学习笔记写作规范

用户要求讲解、润色或扩展课程笔记并输出 Markdown 时，必须写成连贯的教材式教学稿，而不是术语表、公式清单或问答卷。

### 内容组织

- 不机械地按提问顺序逐条回答。先判断缺失了哪些前置概念，再按知识依赖关系重组内容。
- 不要先给结论、定义或公式，再事后解释。每个重要概念依次说明：
  1. 现实问题或学习困难是什么；
  2. 为什么需要引入这个概念；
  3. 它解决了什么问题；
  4. 它与前面概念有什么关系；
  5. 最后才给出正式定义、公式和计算方法。
- 禁止连续堆砌术语、定理和公式而不解释因果关系、使用动机和实际意义。
- 禁止写成“问题：……答案：……”的问答卷；用户的问题应被吸收进一条完整讲解主线。
- 若原始笔记缺少必要前置知识，应主动补齐，即使这些内容未出现在原记录中。
- 若原笔记只有关键词，不逐词扩写；应推断正在学习的知识链并重建连贯说明。
- 控制标题数量；标题体现知识逻辑层次，不为每个术语单独设节。

### 公式与例子

- 每引入一个公式，都解释公式中的变量、描述对象、为什么长成这样，以及在什么场景下有用。
- 公式不能代替解释；直觉、物理意义、简单例子和公式必须相互对应。
- 优先使用少量贯穿全文的例子，展示概念如何逐步解决问题，不为每个结论堆放无关例题。
- 每个重要结论说明适用条件、适用范围和常见误区。
- 段落间有清楚过渡，说明为什么下一步要引入新概念。

### 语言要求

- 使用清楚、连续、面向初学者的解释，不假设读者已经理解教材未说明的概念。
- 专业术语第一次出现时，用通俗语言解释含义和引入原因。
- 可以使用类比，但必须说明类比边界，不能让类比代替严格定义。
- 避免“显然”“容易看出”“只需记住”等跳过关键推理的表达。
- 若存在多种约定或不同教材写法，应说明区别，而不是只给一种写法。

若一段内容删除所有公式后只剩下术语名称和结论，说明解释不充分，必须重新组织。
