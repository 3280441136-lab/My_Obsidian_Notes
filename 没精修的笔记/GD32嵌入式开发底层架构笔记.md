## 1. 为什么从51升级到ARM会变复杂

### 51 的情况

```
用 Keil C51 写代码
    │
    加一个 reg52.h 头文件
    │
    直接写 main()，畅通无阻
```

**原因**：51 架构极其简单，寄存器少，启动过程固定，Keil C51 编译器把启动代码、库全部**内置打包**，用户完全感知不到。

### ARM Cortex-M 的情况

ARM Cortex-M（STM32、GD32、CH32 都是）复杂度不是同一量级：

- 有复杂的内存模型（Flash、RAM 分段）
- 有中断向量表需要配置
- 有时钟系统需要初始化
- 多厂商共用同一内核，需要标准化接口

> **类比**：从骑自行车升级到开手动挡越野车——你得先搞懂离合器和变速箱是干什么的。

## 2. 整体架构层次图

```
┌──────────────────────────────────────────────────────┐
│                  你的代码 (main.c)                    │  ← 你只关注这层
├──────────────────────────────────────────────────────┤
│            外设标准库 / HAL库 / LL库                  │
│   gd32f4xx_gpio.c / gd32f4xx_usart.c / ...          │  ← GD32固件库主体
├──────────────────────────────────────────────────────┤
│              CMSIS + 芯片启动文件                     │
│   startup_gd32f4xx.s  /  system_gd32f4xx.c          │  ← 底层基础设施
├──────────────────────────────────────────────────────┤
│               ARM Cortex-M4 硬件内核                  │  ← 铁疙瘩，寄存器
└──────────────────────────────────────────────────────┘
```

**各层职责一句话总结：**

| 层级 | 代表文件 | 职责 |
|------|----------|------|
| 应用层 | `main.c` | 你的业务逻辑 |
| 外设驱动层 | `gd32f4xx_gpio.c` | 把寄存器操作封装成 C 函数 |
| CMSIS层 | `startup.s` / `system_gd32f4xx.c` | 启动、时钟、内核访问标准化 |
| 硬件层 | 芯片寄存器 | 真实的硬件控制单元 |

## 3. CMSIS 是什么

**CMSIS** = **C**ortex **M**icrocontroller **S**oftware **I**nterface **S**tandard

- 制定者：**ARM 公司本身**（不是 ST，不是 GD，是 ARM 这个 IP 公司）
- 目的：让不同厂商的 ARM 芯片软件能方便移植

```
全世界几十家公司都在用 ARM Cortex-M 内核做芯片：
ST / GD / CH / NXP / Nordic / TI……

内核相同，外设各异
          │
          ▼
ARM 制定 CMSIS 标准
          │
    ┌─────┴──────┐
    │            │
GD32固件库   STM32固件库   CH32固件库
（各自实现，风格相似）
```

**CMSIS 提供的内容：**

| 文件 | 作用 |
|------|------|
| `core_cm4.h` | 访问 Cortex-M4 内核寄存器（NVIC、SysTick等）的标准 C 接口 |
| `core_cmFunc.h` | 开关中断、设置优先级等内核功能函数 |
| `core_cmInstr.h` | 特殊汇编指令的 C 语言封装 |
| `core_cm4_simd.h` | SIMD 数字信号处理指令支持 |

> **类比**：CMSIS 就像 USB-C 标准——充电器和设备来自不同厂商，接口统一，能互通。

## 4. 启动文件 startup.s 详解

### 一个关键问题：按下复位键，芯片第一步做什么？

> **不是 `main()`！** 是 `startup_gd32f4xx.s` 里的汇编代码。

### 启动文件执行流程

```
上电 / 复位
     │
     ▼
① 设置栈指针 SP
  告诉芯片"栈"从内存的哪里开始
     │
     ▼
② 初始化中断向量表
  把所有中断处理函数的地址登记好
     │
     ▼
③ 将 .data 段从 Flash 复制到 RAM
  int x = 5; 这种有初始值的全局变量
  初始值存在 Flash，运行时要复制到 RAM 才能读写
     │
     ▼
④ 将 .bss 段清零
  int y; 这种未初始化的全局变量，清成 0
     │
     ▼
⑤ 调用 SystemInit()
  初始化时钟，让芯片跑到正确频率
     │
     ▼
⑥ 调用 main()   ← 你的代码从这里开始！
```

### 为什么 Keil 里选"否"也能跑？

Keil 安装的**芯片支持包（Device Pack）** 里已经包含了默认 startup 文件，Keil 会自动引用。那个弹窗只是问你**要不要把 .s 文件复制到你的项目目录**，不影响实际编译。

### GD32F4xx 对应的 startup 文件

| 启动文件 | 适用芯片 |
|----------|---------|
| `startup_gd32f405_425.s` | GD32F405 / GD32F425 |
| `startup_gd32f407_427.s` | GD32F407 / GD32F427 |
| `startup_gd32f450_470.s` | GD32F450 / GD32F470 |

> 根据你实际使用的芯片型号选对应的文件！

## 5. GD32 固件标准库详解

### 核心头文件 gd32f4xx.h 做什么

把所有外设寄存器的物理地址，用**结构体 + 宏定义**映射成 C 可访问的变量：

```c
// gd32f4xx.h 内部（简化示意）
#define GPIOA_BASE   0x40020000UL          // GPIOA 寄存器组的起始物理地址
#define GPIOA        ((GPIO_TypeDef *) GPIOA_BASE)  // 强制类型转换为结构体指针

typedef struct {
    __IO uint32_t CTL;    // 控制寄存器，偏移 0x00
    __IO uint32_t OCTL;   // 输出控制寄存器，偏移 0x04
    // ...
} GPIO_TypeDef;
```

这样 `gpio_bit_set(GPIOA, GPIO_PIN_5)` 函数内部才能通过 `GPIOA->OCTL` 操作真实的硬件寄存器。

### 标准库函数的本质

```c
// 最底层：直接写寄存器位（难记、可读性差）
GPIOA->OCTL |= (1 << 5);

// 标准库封装后（gd32f4xx_gpio.c 里的实现）
void gpio_bit_set(uint32_t gpio_periph, uint32_t pin) {
    GPIO_BOP(gpio_periph) = (uint32_t)pin;  // 本质还是操作寄存器
}

// 你调用的样子
gpio_bit_set(GPIOA, GPIO_PIN_5);  // 设置 PA5 为高电平
```

> **标准库的本质**：把寄存器操作**包装成语义明确的 C 函数**，让你不用死记寄存器地址和位操作。

## 6. 标准库 vs HAL库对比

| 对比维度 | 标准库（固件库） | HAL库 |
|---------|----------------|-------|
| 抽象程度 | 直接包裹寄存器 | 更高层抽象 |
| 代码量 | 轻量 | 较重 |
| 运行效率 | **高** | 略低 |
| 上手难度 | 略高（要懂硬件） | 低（配合 CubeMX） |
| 调试难度 | **低**（调用栈浅，好追踪） | 高（调用链深） |
| 答辩讲解 | **好讲**（直接对应硬件） | 抽象太多，难以深入讲解 |
| 竞赛推荐 | ✅ **首选** | 快速原型可用 |

### 竞赛场景建议

```
西门子杯工业嵌入式赛道
         │
    优先使用标准库
         │
    理由：
    ├── 性能好，对硬件控制精准
    ├── 调试容易，出问题好排查
    └── 答辩时能清晰讲解每一步操作的硬件含义
```

## 7. 中断系统：startup.s 与 it.c 的配合

### 核心机制：弱符号（WEAK）

`startup.s` 中用**弱符号**定义所有中断处理函数的默认实现：

```asm
; startup_gd32f407_427.s 内部（简化）
.weak  USART0_IRQHandler
.thumb_set USART0_IRQHandler, Default_Handler   ; 默认指向死循环
```

**弱符号规则**：
- 没人定义这个函数名 → 用默认的（死循环，防止野指针跑飞）
- 有人定义了同名函数 → **链接器自动用你的版本替换**

### 完整的中断调用链

```
你在 gd32f4xx_it.c 里实现函数：
void USART0_IRQHandler(void) {
    // 你的串口接收处理逻辑
}

          ↓ 编译成 it.o

链接器合并所有 .o 文件
发现 it.o 里有强符号 USART0_IRQHandler
覆盖 startup.o 里的弱符号默认实现

          ↓

最终 hex 文件中：
向量表 → USART0_IRQHandler 地址 → 你写的函数

          ↓ 串口中断触发时

硬件自动查向量表 → 跳转到你的函数执行
```

### 为什么 it.c 不需要被 #include

| 机制 | .h 头文件 | .c 源文件 |
|------|----------|----------|
| 引入方式 | `#include`（编译期文本展开） | 加入 Keil 工程文件列表 |
| 连接方式 | 声明/类型定义 | 链接器靠**函数名匹配**自动绑定 |

`it.c` 只需要出现在 **Keil 工程树**里，链接器就能找到它，不需要任何文件 `#include` 它。

### 三个文件的角色

| 文件 | 属于 | 职责 |
|------|------|------|
| `startup_gd32f4xx.s` | 固件库 | 登记中断向量表（函数名列表），提供弱符号默认实现 |
| `gd32f4xx_it.c` | 你的项目 | 实现中断函数的实际逻辑（强符号，覆盖弱符号） |
| `gd32f4xx_it.h` | 你的项目 | 声明 it.c 里的函数原型（给外部调用时用） |

## 8. 头文件引用链（#include链）

### 完整引用路径

```
你的 main.c
    │
    └── #include "gd32f4xx.h"          ← 你只写这一行
              │
              │（条件编译，见第9节）
              │
              └── #include "gd32f4xx_libopt.h"    ← 放在你的项目文件夹里
                        │
                        ├── #include "gd32f4xx_rcu.h"    ← 时钟使能（必须）
                        ├── #include "gd32f4xx_gpio.h"
                        ├── #include "gd32f4xx_usart.h"
                        ├── #include "gd32f4xx_timer.h"
                        └── ...（libopt.h 里开启哪些就包含哪些）
```

### gd32f4xx_libopt.h 的内容

```c
// gd32f4xx_libopt.h —— 按需注释掉不用的外设
#if defined(GD32F407) || defined(GD32F405) || ...
    #include "gd32f4xx_rcu.h"       // ← 必须保留！
    #include "gd32f4xx_gpio.h"
    #include "gd32f4xx_usart.h"
    #include "gd32f4xx_timer.h"
    #include "gd32f4xx_dma.h"
    // #include "gd32f4xx_dac.h"    // 注释掉 = 不编译这个外设库
    // ...
#endif
```

### 防止循环包含

各外设头文件自己也会 `#include "gd32f4xx.h"`（为了使用寄存器定义），但不会死循环，因为每个头文件都有**包含守卫**：

```c
// gd32f4xx_gpio.h 开头
#ifndef GD32F4XX_GPIO_H       // 如果还没包含过
#define GD32F4XX_GPIO_H       // 标记为已包含
// ... 头文件内容 ...
#include "gd32f4xx.h"
#endif                        // 第二次包含时直接跳过
```

## 9. 预处理宏机制

### 什么是预处理宏

预处理宏是编译开始**之前**就完成的文本替换。`#define GD32F407` 相当于在所有代码第一行插入这个定义，后续 `#if defined(GD32F407)` 才能生效。

### 为什么必须定义芯片型号宏

查看 `gd32f4xx.h` 第46行的真实代码：

```c
// 如果没有定义任何芯片型号，直接报错
#if !defined(GD32F450) && !defined(GD32F405) && !defined(GD32F407) ...
  #error "Please select the target GD32F4xx device in gd32f4xx.h file"
#endif

// 不同芯片型号对应不同的寄存器定义
#if defined(GD32F407) || defined(GD32F427)
    // F407 的中断号列表、外设地址...  只有定义了 GD32F407 这段才编译
#endif

#if defined(GD32F450) || defined(GD32F470)
    // F450 的...
#endif
```

同一个 `gd32f4xx.h` 里装了所有芯片型号的定义，靠宏来**选择编译哪一段**。

### 关于 USE_STDPERIPH_DRIVER

```c
// gd32f4xx.h 第359行的真实代码
#if !defined USE_STDPERIPH_DRIVER
#define USE_STDPERIPH_DRIVER    // 如果没定义，自动定义它
#endif
#ifdef USE_STDPERIPH_DRIVER
#include "gd32f4xx_libopt.h"   // 然后包含 libopt.h
#endif
```

> **结论**：这个版本（V3.3.3）会**自动定义** `USE_STDPERIPH_DRIVER`，Keil 的 Define 框里**只需要填芯片型号**（如 `GD32F407`），`USE_STDPERIPH_DRIVER` 可以不填。

## 10. 编译工具链

### Keil 里的编译流程

```
你的 .c / .s 文件
        │
        ▼ 编译器（Keil 用 ARMCC/AC6，开源生态用 arm-none-eabi-gcc）
        │
        ▼ 链接器（把所有 .o 文件合并，按链接脚本分配内存地址）
        │
        ▼ .hex / .bin 文件
        │
        ▼ 烧录器（JLink / DAP-Link / ST-Link）
        │
        ▼ 芯片运行
```

### GCC vs Keil ARMCC

| | GCC（arm-none-eabi-gcc） | Keil ARMCC/AC6 |
|-|--------------------------|----------------|
| 费用 | 免费开源 | 商业授权（MDK有限制） |
| 使用方式 | 命令行 / VS Code / CLion | Keil IDE |
| 生态 | Linux友好，CI/CD方便 | Windows友好，初学者友好 |
| 竞赛推荐 | 不推荐（配置复杂） | ✅ **推荐** |

> **你现在用 Keil，不需要关心 GCC**。GCC 是开源生态的玩法，Keil 自带编译器，一键 Build 搞定。

| 文件 | 放在哪 | 来自哪里 | 你要怎么处理 |

## 12. 新建 Keil 工程全流程

### 推荐的工程文件夹结构

```
你的工程文件夹/
├── MyProject.uvprojx       ← Keil 工程文件
├── main.c                  ← 你写的主程序
├── gd32f4xx_it.c           ← 从 Examples 里任意一个例程复制
├── gd32f4xx_it.h           ← 同上
└── gd32f4xx_libopt.h       ← 同上
```

固件库文件**不需要复制**，在 Keil 里直接引用原路径。

### 第一步：建工程分组并添加文件

在 Keil 左边工程树右键 `Add Group`，建如下分组：

```
MyProject（工程）
├── Application                ← 添加：main.c, gd32f4xx_it.c
│
├── CMSIS                      ← 添加以下两个文件（从 Firmware 路径里找）：
│   ├── system_gd32f4xx.c          (Firmware/CMSIS/GD/GD32F4xx/Source/)
│   └── startup_gd32f407_427.s     (Firmware/CMSIS/GD/GD32F4xx/Source/ARM/)
│                                    ↑ 根据实际芯片型号选
│
└── StdPeriph_Driver           ← 添加你用到的外设 .c 文件：
    ├── gd32f4xx_rcu.c             (必加！任何外设都需要开时钟)
    ├── gd32f4xx_gpio.c            (用 GPIO 加)
    ├── gd32f4xx_usart.c           (用串口加)
    ├── gd32f4xx_misc.c            (建议加，NVIC 中断控制)
    └── ...（用什么加什么）
```

### 第二步：配置头文件搜索路径

`Options for Target` → `C/C++` → `Include Paths`，添加：

```
路径1：...\Firmware\CMSIS\
路径2：...\Firmware\CMSIS\GD\GD32F4xx\Include\
路径3：...\Firmware\GD32F4xx_standard_peripheral\Include\
路径4：你的工程文件夹\          ← 让编译器找到 libopt.h 和 it.h
```

### 第三步：添加预处理宏

同一个 `C/C++` 页面，`Define` 框填写芯片型号：

```
GD32F407
```

（根据你实际使用的芯片型号填写，如 GD32F405 则填 `GD32F405`）

### 第四步：选择芯片型号

`Options for Target` → `Device` → 搜索并选择你的芯片

### 配置完成后的数据流

```
main.c 里写 #include "gd32f4xx.h"
    │
    ▼ 编译器展开（根据 GD32F407 宏选择正确的寄存器定义）
    │
    ▼ gd32f4xx.h → gd32f4xx_libopt.h → gd32f4xx_gpio.h 等
    │
Keil 编译所有加入工程的 .c 和 .s 文件
    │
链接器：startup.s 向量表 + it.c 中断函数 → 符号绑定
    │
    ▼ 输出 .hex 文件 → 烧录到芯片
```

### 模板工程使用策略

> **配一次，永远复制。**
> 第一次花 20 分钟把模板工程配好跑通，之后每次新建工程就**复制整个文件夹改个名字**，30 秒搞定。

## 13. Manage Run-Time Environment 说明

新建 Keil 工程时弹出的 **"Manage Run-Time Environment"** 对话框，是 Keil 的 **Pack 包管理系统**界面。

### 各选项该不该勾

| 选项 | 是否勾选 | 原因 |
|------|---------|------|
| CMSIS → CORE | ✅ 勾 | Keil 自动添加 `core_cm4.h` 等头文件路径，省去手动配置 |
| Device → Startup | ❌ 不勾 | 你已手动添加 `startup_gd32f4xx.s`，勾了会有两个启动文件冲突 |
| 外设驱动相关 | ❌ 不勾 | 你用的是自己下载的固件库，不用 Pack 里的版本 |

### 为什么 CMSIS-CORE 和固件库里的不冲突

`core_cm4.h` 是 ARM 官方标准文件，Pack 里的和 `Firmware/CMSIS/` 里的内容完全相同。头文件有 `#ifndef` 守卫，重复包含不会报错。勾选 CMSIS-CORE 只是让 Keil 自动管理这个路径，更方便。

## 14. CH340 vs CH341 对比

两者都是**南京沁恒**出品的 USB 转串口芯片，常见于开发板和调试模块。

### 功能对比

| 功能 | CH340 | CH341 |
|------|-------|-------|
| USB 转 UART（串口） | ✅ | ✅ |
| USB 转 I2C | ❌ | ✅ |
| USB 转 SPI | ❌ | ✅ |
| USB 转并口 | ❌ | ✅ |
| 价格 | 更便宜 | 略贵 |
| 常见形态 | 蓝色/黑色 USB-TTL 小模块 | CH341A 黑色编程器 |

### 典型应用场景

**CH340** — 嵌入式开发日常调试：
```
电脑 USB ──→ CH340 ──→ MCU 的 TX/RX 引脚
                         ├── 串口打印调试信息
                         └── ISP方式烧录程序（部分芯片支持）
```

**CH341** — 芯片编程/救砖：
```
电脑 USB ──→ CH341A 编程器 ──SPI──→ BIOS Flash 芯片
                                      └── 直接读写 Flash 内容
```

### 嵌入式开发选哪个

> 做 GD32 / STM32 开发，串口调试和程序下载，**买 CH340 就够了**。
>
> CH341 只在需要直接操作 SPI/I2C 存储芯片（烧录 BIOS、读写独立 EEPROM）时才用得上。

## 附：关键概念速查表

| 概念 | 一句话解释 |
|------|-----------|
| CMSIS | ARM 公司制定的内核访问标准，让不同厂商芯片软件可移植 |
| startup.s | 上电后第一个运行的汇编文件，初始化栈、向量表，最终调用 main() |
| 中断向量表 | 存放所有中断处理函数地址的表，startup.s 里定义 |
| 弱符号（WEAK） | startup.s 的默认中断处理，可被 it.c 里的同名函数自动覆盖 |
| gd32f4xx.h | 总头文件，把寄存器物理地址映射成 C 结构体 |
| gd32f4xx_libopt.h | 项目级开关面板，控制编译哪些外设库 |
| 标准库 | 把寄存器操作封装成 C 函数，如 `gpio_bit_set()` |
| HAL库 | 更高层抽象，移植性好但代码重，调试难 |
| 预处理宏 | 编译前的全局定义，`GD32F407` 告诉头文件你用哪款芯片 |
| GCC | 开源编译器，Keil 用自己的 ARMCC，原理一样 |
| CH340 | 纯 USB 转串口，嵌入式调试首选 |
| CH341 | USB 转串口/I2C/SPI，常用于 BIOS 编程器 |
