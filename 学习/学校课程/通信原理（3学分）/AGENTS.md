## 教学型学习笔记写作规范

当用户要求讲解、润色或扩展课程笔记时，必须把内容写成一份连贯的教材式教学稿，而不是术语表、公式清单或问答卷。

### 核心要求

- 不要机械地按照用户提问的顺序逐条回答。先判断用户缺失了哪些前置概念，再按照知识依赖关系重新组织内容。
- 不要先给结论、定义或公式，再事后补充解释。每个重要概念都应先说明：
  1. 现实问题或学习困难是什么；
  2. 为什么需要引入这个概念；
  3. 这个概念解决了什么问题；
  4. 它与前面概念有什么关系；
  5. 最后再给出正式定义、公式和计算方法。
- 禁止把多个术语、定理和公式连续堆砌，却不解释它们之间的因果关系、使用动机和实际意义。
- 禁止把正文写成“问题：……答案：……”的问答卷形式。用户的问题应被吸收进一条完整的讲解主线中。
- 如果用户的原始笔记缺少必要前置知识，应主动补齐这些知识，即使这些内容没有出现在用户的原始记录中。
- 如果原笔记只记录了关键词，不要逐个关键词扩写；应根据关键词推断用户正在学习的知识链，并重建一份连贯的教材式说明。
- 每引入一个公式，都必须解释公式中的变量、公式描述的对象、公式为什么长成这样，以及它在什么场景下有用。
- 公式不能代替解释。直觉解释、物理意义、简单例子和公式之间必须相互对应。
- 每个重要结论都应说明适用条件、适用范围以及容易误用的地方。
- 优先使用少量贯穿全文的例子，展示概念如何一步步解决问题，不要为每个结论堆放彼此无关的例题。
- 段落之间必须有清楚的过渡，说明“为什么下一步要引入这个概念”。
- 控制标题数量，标题应体现知识的逻辑层次，而不是把每个术语单独列成一个小节。
- 教学目标是让读者理解“为什么这样定义、为什么这样变换、什么时候使用”，而不只是记住结论。

### 推荐的讲解顺序

对于数学、信号与系统、数字信号处理等抽象课程，优先采用以下教学链条：

1. 先说明研究对象和实际问题；
2. 回顾理解当前内容所必需的前置知识；
3. 从直觉或具体例子发现问题；
4. 说明为什么需要新的概念或工具；
5. 给出正式定义和数学表达；
6. 通过一个简单例子展示公式如何工作；
7. 解释该工具与前面知识的联系；
8. 说明适用条件、局限和常见误区；
9. 最后再给出简短的记忆线索或复习路线。

### 语言要求

- 使用清楚、连续、面向初学者的解释，不假设用户已经理解教材中未说明的概念。
- 专业术语第一次出现时，必须用通俗语言解释其含义和引入原因。
- 可以使用类比，但必须说明类比的边界，不能让类比替代严格定义。
- 避免“显然”“容易看出”“只需记住”等跳过关键推理的表达。
- 如果存在多个约定或不同教材写法，应说明它们的区别，而不是只给出其中一种写法。

若一段内容删除所有公式后就只剩下术语名称和结论，说明解释不充分，必须重新组织。

### Mermaid 本课概要

- 每篇按课次编号的课程笔记都必须在一级标题之后、其他导语或正文之前设置 `## 本课概要`，并紧接一个 Mermaid `mindmap` 代码块。
- 概要必须是以本课主题为根节点的知识思维导图，通常设置 3 至 5 个一级分支，并在需要时继续展开二级分支，呈现核心概念、关键关系、分析或计算方法、应用以及易错点。
- 分支必须反映知识结构，不能把课程错误地画成单条线性流程，也不能只是机械抄录正文目录或仅作装饰。
- 节点文字应简短明确；同级节点表达并列知识，不同层级表达包含、分类或依赖关系。
- Mermaid 节点内不写 LaTeX 公式；涉及变量和公式时用简短中文概念概括，严格数学表达放在正文中，以保证 Obsidian 稳定渲染。
- 新建笔记时必须添加该思维导图；修改既有课程笔记时，也要检查并补齐或同步更新概要。

## 课程笔记工作约定

开始回答本课程的新问题前，先读取当前文件夹下的 `README.md` 和 `第*.md` 文件，确认已经学过的章节、尚未解决的问题和符号约定。课堂问题若只提供关键词、讲课脉络或疑问，应先结合已有笔记还原教学背景，再按知识依赖关系讲解。

只有用户明确要求整理成笔记时，才把对话内容写入 Markdown 文件。笔记按“第 N 课”编号，并根据国内通信原理教材的知识链重新划分，不让相邻课堂内容互相耦合。Markdown 中行内公式使用 `$...$`，独立公式使用 `$$...$$`；聊天回复仍使用 `\(...\)` 和 `$$...$$`。

## SVG 数学排版硬性约束

SVG 不是 Markdown，也不是 LaTeX/MathJax 环境。SVG 中的 `<text>` 只会显示字面字符，因此禁止把 `R_B`、`x_k`、`log_2`、`x^2` 或 `$$...$$` 直接写进 SVG 文本。这样写会产生普通下划线、尖号或反斜杠，而不会形成真正的数学排版。

所有 SVG 数学公式必须真正渲染，不能只是把 LaTeX 源码显示出来。优先使用 SVG 内嵌 MathML 数学排版；如果目标阅读器对外部 MathML 或 `<foreignObject>` 支持不稳定，则使用公式渲染器生成 SVG 路径后嵌入。简单上下标可以使用 `tspan`，但复杂公式、求和号、对数、条件竖线和不等式必须经过实际公式渲染，不得手写拼接普通文本。

### 上下标和公式写法

- 下标必须使用 `<tspan baseline-shift="sub" font-size="0.72em">...</tspan>`。
- 上标必须使用 `<tspan baseline-shift="super" font-size="0.72em">...</tspan>`。
- 一个公式中有多个上下标时，每个上下标分别使用独立的 `tspan`，不要用 `_` 或 `^` 连接。
- 公式中需要继续书写正常基线内容时，使用新的 `tspan`，避免继承偏移。
- 复杂公式优先拆成多个 `<text>` 或多个 `<tspan x="..." dy="...">`，保证窄屏下不重叠、不溢出。
- MathML 公式应放在 SVG 的 `<foreignObject>` 中的 XHTML `<math>` 节点，使用 `http://www.w3.org/1998/Math/MathML` 命名空间，并在目标阅读器中实际检查。
- 如果使用公式渲染器生成 SVG 路径，应保留可读的 `<title>`、`<desc>` 和无障碍文本，不得只留下无法识别的轮廓。

正确示例：

```xml
<text>R<tspan baseline-shift="sub" font-size="0.72em">B</tspan>=1/T<tspan baseline-shift="sub" font-size="0.72em">B</tspan></text>
```

```xml
<text>I(x<tspan baseline-shift="sub" font-size="0.72em">k</tspan>)=-log<tspan baseline-shift="sub" font-size="0.72em">2</tspan> p(x<tspan baseline-shift="sub" font-size="0.72em">k</tspan>)</text>
```

禁止示例：

```xml
<text>R_B=1/T_B</text>
<text>I(x_k)=-log_2 p(x_k)</text>
<text>x^2+y^2</text>
```

### SVG 公式符号和可读性

- 公式中的变量、常数和函数名应使用真正的公式排版结构；不要把 LaTeX 命令留在 SVG 中。
- 希腊字母、求和号、对数、条件竖线和不等式必须使用 MathML 或渲染后的 SVG 路径，并通过 `<title>`、`<desc>` 给出完整解释；不要把整段 LaTeX 当作 SVG 文本。
- 每张 SVG 必须有 `<title>` 和 `<desc>`，说明图示对象、关键关系和阅读顺序。
- 图中所有文字必须在实际渲染后检查，重点关注脚标高度、基线、中文与英文混排、箭头遮挡、文字溢出和边界裁切。
- 公式标注应直接靠近对应模块或曲线，不把关键公式挤在图外，也不通过缩小字号掩盖布局问题。

### 交付前检查

1. 对每个 SVG 执行 XML 解析检查。
2. 检查 SVG 文本中不存在裸露的 `_`、`^`、`\`、`$` 数学语法或未渲染的 LaTeX 源码。
3. 用 Chrome/Edge 或 Obsidian 实际渲染 SVG，逐张检查 MathML/公式路径、上下标、求和号、对数、条件竖线和不等式。
4. 新增或修改 SVG 后，检查引用它的 Markdown 嵌入路径是否仍然有效。
5. 只有在渲染检查通过后，才把 SVG 纳入笔记。
